**TL;DR** — Each conversation is saved as an append-only JSONL file where every entry carries a unique `id` and a `parentId` that points to its predecessor, forming a tree rather than a flat list. This tree structure is what makes branching possible: you can rewind to any earlier message and continue down a new path without touching the original history. By the end of this chapter you'll understand the file format, how to navigate and branch the tree, and how the agent discovers sessions for a given working directory.

# Sessions, Branching, and the Session Tree

Before we look at the file format, let's be clear about the problem we're solving.

A flat conversation log is easy: append each message to an array. But what happens when a user decides the last three messages were wrong and wants to try a different approach? With a flat list, you'd have to delete those messages — and they're gone. The user can't come back to the original path later.

We want something better: the ability to rewind to any earlier message, continue in a new direction, and still have both paths available afterward. That requires a *tree*, not a list.

The `SessionManager` class (in `src/core/session-manager.ts`) implements exactly that: it stores every entry in an append-only JSONL file where entries are linked by `id`/`parentId` pairs. The current position in the conversation is tracked by a single "leaf pointer" (`leafId`). Branching is a matter of moving that pointer to an earlier entry.

> **Prerequisite:** This chapter builds on `AgentSession`, the higher-level object that owns session switching and branching at the UX layer. If you haven't read that chapter, see [AgentSession Core](./agent-session-core.md) for a two-minute orientation — the present chapter focuses on the lower-level storage format and operations that `AgentSession` delegates to `SessionManager`.

## Step 1 — The JSONL file: one JSON object per line

Let's start with the physical format. A session file is a `.jsonl` file (JSON Lines), meaning every line is a self-contained JSON object. You can open one in any text editor or `cat` it in a terminal and read it entry by entry.

The file always begins with a **session header** on the very first line:

```jsonc
// Line 1 — session header (type: "session")
{"type":"session","version":3,"id":"01935f2a-abc1-7000-0000-000000000001","timestamp":"2024-11-01T10:00:00.000Z","cwd":"/home/user/my-project"}
```

| Field | Type | What it is |
|---|---|---|
| `type` | `"session"` | Always `"session"` — distinguishes the header from ordinary entries |
| `version` | `number` | Schema version; current is `3` |
| `id` | `string` | Unique identifier for this session (UUIDv7) |
| `timestamp` | `string` | ISO-8601 creation time |
| `cwd` | `string` | Working directory where the session was started |
| `parentSession` | `string?` | Path to a parent session file, if this session was forked from another |

After the header, every subsequent line is a **session entry**. Each entry shares this base shape:

```jsonc
// SessionEntryBase — every non-header entry has these fields
{
  "type": "message",   // what kind of entry this is
  "id": "a1b2c3d4",   // 8-character hex ID, unique within this file
  "parentId": "...",  // id of the parent entry, or null for the first entry
  "timestamp": "..."  // ISO-8601 timestamp
}
```

The `id` is a short 8-character hex string generated by sampling from `randomUUID()` and checking for collisions. The `parentId` is the id of the entry this one follows in the conversation. The very first entry has `parentId: null` — it is the root of the tree.

### Entry types

The `type` field determines what extra fields are present. Here is the complete set:

| `type` | Purpose |
|---|---|
| `"message"` | A conversation message (user, assistant, tool calls, etc.) |
| `"compaction"` | A summary that replaces earlier messages to save context |
| `"branch_summary"` | A summary of the path that was abandoned when branching |
| `"thinking_level_change"` | Records a change in the model's extended thinking setting |
| `"model_change"` | Records a model or provider switch |
| `"label"` | A user-defined bookmark on a specific entry |
| `"session_info"` | Metadata like a user-defined session display name |
| `"custom"` | Extension-specific data (does not enter LLM context) |
| `"custom_message"` | Extension-injected content that does enter LLM context |

We'll look at `compaction`, `branch_summary`, and `label` entries in detail later. For now let's build up the core tree.

## Step 2 — The parentId links form a tree

Here's a minimal sequence after two user/assistant turns:

```jsonc
{"type":"session","version":3,"id":"sess-001","timestamp":"...","cwd":"/home/user/proj"}
{"type":"message","id":"aa000001","parentId":null,"timestamp":"...","message":{"role":"user","content":"Say hello"}}
{"type":"message","id":"bb000002","parentId":"aa000001","timestamp":"...","message":{"role":"assistant","content":"Hello!"}}
{"type":"message","id":"cc000003","parentId":"bb000002","timestamp":"...","message":{"role":"user","content":"Say goodbye"}}
{"type":"message","id":"dd000004","parentId":"cc000003","timestamp":"...","message":{"role":"assistant","content":"Goodbye!"}}
```

Follow the `parentId` arrows and you get this chain:

```
(root)
  aa000001  [user: "Say hello"]
    └─ bb000002  [assistant: "Hello!"]
         └─ cc000003  [user: "Say goodbye"]
              └─ dd000004  [assistant: "Goodbye!"]
```

The `leafId` pointer sits at `dd000004`. When the session manager needs to reconstruct the conversation for the LLM, it walks from the leaf up to the root (via `parentId` hops), reverses the path, and hands the ordered list of messages to `buildSessionContext()`.

```ts
// Simplified view of getBranch() — walks leaf → root, returns root → leaf
getBranch(fromId?: string): SessionEntry[] {
  const path: SessionEntry[] = [];
  const startId = fromId ?? this.leafId;
  let current = startId ? this.byId.get(startId) : undefined;
  while (current) {
    path.unshift(current); // prepend so result is root-first
    current = current.parentId ? this.byId.get(current.parentId) : undefined;
  }
  return path;
}
```

`this.byId` is a `Map<string, SessionEntry>` built when the file is loaded — O(1) lookup for any entry by id.

## Step 3 — Branching: moving the leaf pointer

Now we have a problem. Suppose the user decides "Say goodbye" was wrong and wants to go back to the moment after "Hello!" and try something different instead.

With our tree, this is simple. We don't delete anything. We only **move the leaf pointer** to `bb000002` — the entry for the assistant's "Hello!" reply:

```ts
// branch() — move leafId to any earlier entry
branch(branchFromId: string): void {
  if (!this.byId.has(branchFromId)) {
    throw new Error(`Entry ${branchFromId} not found`);
  }
  this.leafId = branchFromId;
}
```

Now the next `appendMessage()` call will create a new entry whose `parentId` is `bb000002`. The file grows:

```jsonc
{"type":"message","id":"ee000005","parentId":"bb000002","timestamp":"...","message":{"role":"user","content":"Tell me a joke"}}
{"type":"message","id":"ff000006","parentId":"ee000005","timestamp":"...","message":{"role":"assistant","content":"Why did the..."}}
```

The tree now has **two branches** growing from `bb000002`:

```
aa000001  [user: "Say hello"]
  └─ bb000002  [assistant: "Hello!"]     ← branch point
       ├─ cc000003  [user: "Say goodbye"]   (original path, abandoned)
       │    └─ dd000004  [assistant: "Goodbye!"]
       └─ ee000005  [user: "Tell me a joke"]   (new branch)
            └─ ff000006  [assistant: "Why did the..."]
```

Both paths exist in the same file. Neither was deleted. The `leafId` now sits at `ff000006`. `getBranch()` from `ff000006` gives us `[aa000001, bb000002, ee000005, ff000006]` — the new path — while `cc000003` and `dd000004` are still in the file and reachable by calling `getBranch("dd000004")`.

### Resetting the leaf to before the first entry

What if the user wants to re-edit the very first message — before any entry exists? There's a special case for that:

```ts
// resetLeaf() — sets leafId to null
// The next appendMessage() creates a new root (parentId = null)
resetLeaf(): void {
  this.leafId = null;
}
```

This creates a second root in the tree. The session manager's documentation notes that a "well-formed session has exactly one root", but orphaned entries with `parentId === null` are returned as additional roots rather than causing an error.

## Step 4 — Visualising the tree with getTree()

The `getTree()` method builds an in-memory tree of `SessionTreeNode` objects that mirrors the parentId structure. It's useful for UI code that needs to render the branching history panel.

```ts
// SessionTreeNode — one node per session entry
interface SessionTreeNode {
  entry: SessionEntry;       // the entry itself
  children: SessionTreeNode[]; // direct children (sorted oldest-first)
  label?: string;            // resolved label/bookmark for this entry, if any
  labelTimestamp?: string;   // timestamp of the latest label change
}
```

`getTree()` returns an array of *root* nodes (normally just one). Each root's `children` array holds its direct successors; those successors have their own `children`, and so on. Children within a node are sorted by timestamp (oldest first, newest at the bottom), so the rendered tree reads chronologically at every level.

The tree structure for our two-branch example above would look like this:

```
roots: [
  SessionTreeNode(aa000001) {
    children: [
      SessionTreeNode(bb000002) {
        children: [
          SessionTreeNode(cc000003) { children: [SessionTreeNode(dd000004)] },
          SessionTreeNode(ee000005) { children: [SessionTreeNode(ff000006)] }
        ]
      }
    ]
  }
]
```

## Step 5 — Special entries: compaction, branch summaries, and labels

The tree can contain more than messages. Let's look at the three special entry types you'll encounter in real sessions.

### Compaction entries

When a conversation grows very long, the agent compacts it: older messages are replaced with a prose summary to keep the context window under control. The compaction is recorded as a `"compaction"` entry:

```ts
interface CompactionEntry extends SessionEntryBase {
  type: "compaction";
  summary: string;         // text summary of the compacted messages
  firstKeptEntryId: string; // id of the earliest message that is NOT summarised
  tokensBefore: number;    // token count before compaction
  details?: unknown;       // extension-specific structured data
  fromHook?: boolean;      // true if an extension generated this compaction
}
```

When `buildSessionContext()` encounters a compaction entry along the path from root to leaf, it:
1. Emits the `summary` text as the first "message" the LLM will see.
2. Skips all entries *before* the compaction that are *before* `firstKeptEntryId`.
3. Includes entries from `firstKeptEntryId` up to (but not including) the compaction entry.
4. Includes all entries *after* the compaction normally.

This means the LLM always sees a coherent conversation: a brief summary of history it no longer has in full, followed by the messages that remain intact.

### Branch summary entries

When the user branches with `branchWithSummary()` instead of plain `branch()`, a `"branch_summary"` entry is appended right at the branch point:

```ts
interface BranchSummaryEntry extends SessionEntryBase {
  type: "branch_summary";
  fromId: string;          // the entry id that was branched from (or "root")
  summary: string;         // prose summary of the abandoned path
  details?: unknown;       // extension-specific data
  fromHook?: boolean;
}
```

```ts
// branchWithSummary() — branch + record a summary of what we're leaving behind
branchWithSummary(
  branchFromId: string | null,
  summary: string,
  details?: unknown,
  fromHook?: boolean,
): string {
  if (branchFromId !== null && !this.byId.has(branchFromId)) {
    throw new Error(`Entry ${branchFromId} not found`);
  }
  this.leafId = branchFromId;
  // ... appends a branch_summary entry as a child of branchFromId
}
```

In `buildSessionContext()`, a `branch_summary` entry along the current path is converted into a special user message so the LLM knows it picked up partway through an alternative conversation path.

### Label entries

Labels are user-defined bookmarks. You can attach a text label to any entry id, and it persists in the file as a `"label"` entry:

```ts
interface LabelEntry extends SessionEntryBase {
  type: "label";
  targetId: string;        // the entry being bookmarked
  label: string | undefined; // undefined or empty string to clear the label
}
```

```ts
// appendLabelChange() — set or clear a label on any entry
appendLabelChange(targetId: string, label: string | undefined): string
```

Labels are maintained in a `Map<string, string>` (`labelsById`) that is rebuilt when the file is loaded. The latest `label` entry for a given `targetId` wins — passing `undefined` or an empty string clears it. `getTree()` resolves labels and attaches them to the corresponding `SessionTreeNode` so UI code doesn't need to do its own lookup.

## Step 6 — Creating a branched session file (clone)

Sometimes you want not only a leaf pointer change but a clean new file containing only one path through the tree — useful for handing off a specific conversation to another tool or for archiving.

`createBranchedSession(leafId)` does exactly this:

```ts
// Simplified view of createBranchedSession()
createBranchedSession(leafId: string): string | undefined {
  const path = this.getBranch(leafId);  // root → leaf, only the chosen path
  // ...
  // Write new header with parentSession = current session file
  // Write path entries (label entries are rebuilt from resolved map)
  // Update this.sessionId, this.sessionFile, this.fileEntries, rebuild index
  return newSessionFile; // path to the new .jsonl file
}
```

The new file gets:
- A fresh `sessionId` (new UUIDv7).
- A `parentSession` field in the header pointing back to the original file (so the lineage is traceable).
- The same `cwd` as the source session.
- All entries on the `root → leafId` path (label entries are excluded from the path itself and re-appended at the end, since they are logically metadata rather than conversation nodes).

After `createBranchedSession()` returns, the `SessionManager` instance is now managing the new file. The original file is untouched.

## Step 7 — Forking across working directories (forkFrom)

There's a related operation for a different scenario: you have a session from project A and want to continue it in project B, with B's working directory. The static `SessionManager.forkFrom()` method handles this:

```ts
// Simplified view of SessionManager.forkFrom()
static forkFrom(
  sourcePath: string,   // path to the source .jsonl file
  targetCwd: string,    // working directory for the new session
  sessionDir?: string,  // where to store the new file (defaults to ~/.xzy/ path for targetCwd)
  options?: NewSessionOptions,
): SessionManager
```

What it does:
1. Loads all entries from the source file.
2. Creates a new `.jsonl` file under `targetCwd`'s session directory.
3. Writes a new header with the new session id, `targetCwd` as `cwd`, and the source path as `parentSession`.
4. Copies every non-header entry verbatim from the source.

The id/parentId chain is preserved exactly — the tree structure carries over. The `parentSession` field in the header is the breadcrumb back to the origin.

The test suite verifies the forking scenarios (S87):

```ts
// From the test: fork from a single message
it("should allow forking from single message", async () => {
  await session.prompt("Say hello");
  await session.agent.waitForIdle();

  const userMessages = session.getUserMessagesForForking();
  expect(userMessages.length).toBe(1);
  expect(userMessages[0].text).toBe("Say hello");

  const result = await runtimeHost.fork(userMessages[0].entryId);
  expect(result.cancelled).toBe(false);
  // After the fork, the session has rewound: 0 messages visible
  expect(session.messages.length).toBe(0);
  // The new session file was created on disk
  expect(existsSync(session.sessionFile!)).toBe(false); // not yet written (no assistant yet)
});
```

The test also covers forking from the middle of a multi-turn conversation and in-memory (no-file) mode:

```ts
// Fork from turn 2 of a 3-turn conversation
it("should fork from middle of conversation", async () => {
  await session.prompt("Say one");
  await session.prompt("Say two");
  await session.prompt("Say three");

  const userMessages = session.getUserMessagesForForking();
  expect(userMessages.length).toBe(3);

  const result = await runtimeHost.fork(userMessages[1].entryId); // fork at "Say two"
  // After fork, session has only the first turn (user + assistant)
  expect(session.messages.length).toBe(2);
  expect(session.messages[0].role).toBe("user");
  expect(session.messages[1].role).toBe("assistant");
});

// In-memory mode: forking works even without a session file
it("should support in-memory forking in --no-session mode", async () => {
  await createSession(true); // noSession = true → SessionManager.inMemory()
  expect(session.sessionFile).toBeUndefined();

  await session.prompt("Say hi");
  const result = await runtimeHost.fork(userMessages[0].entryId);

  expect(session.messages.length).toBe(0);
  expect(session.sessionFile).toBeUndefined(); // still no file in no-session mode
});
```

## Step 8 — cwd-scoped discovery: finding sessions for the current project

When you run `xzy` in a project directory, it needs to find any existing sessions for that directory — not sessions from other projects. Here's how `SessionManager` implements this.

### Where session files live

By default, session files are stored under `~/.xzy/sessions/<encoded-cwd>/`, where `<encoded-cwd>` is a file-system-safe encoding of the absolute path. The encoding is:

```ts
// From getDefaultSessionDirPath() — simplified
const safePath = `--${resolvedCwd.replace(/^[/\\]/, "").replace(/[/\\:]/g, "-")}--`;
// e.g. /home/user/my-project → --home-user-my-project--
return join(agentDir, "sessions", safePath);
```

Each working directory gets its own subdirectory under `~/.xzy/sessions/`. Sessions from different projects never share a directory.

### Session file names

Each `.jsonl` file is named `<timestamp>_<sessionId>.jsonl` where `<timestamp>` is the ISO creation time with `:` and `.` replaced by `-`. This makes them sort chronologically by filename, even though the session manager also uses `mtime` for ordering.

### Finding the most recent session

`findMostRecentSession(sessionDir, cwd?)` scans a session directory and returns the path of the most recently modified `.jsonl` file:

```ts
// Simplified view of findMostRecentSession()
function findMostRecentSession(sessionDir: string, cwd?: string): string | null {
  const files = readdirSync(sessionDir)
    .filter(f => f.endsWith(".jsonl"))
    .map(f => ({ path: join(sessionDir, f), header: readSessionHeader(f) }))
    .filter(file => file.header !== null
      && (!cwd || resolvePath(file.header.cwd) === resolvePath(cwd)))
    .map(({ path }) => ({ path, mtime: statSync(path).mtime }))
    .sort((a, b) => b.mtime.getTime() - a.mtime.getTime());

  return files[0]?.path || null;
}
```

The optional `cwd` filter compares the resolved cwd stored in each file's header against the requested cwd. This matters when a custom `sessionDir` is shared across projects — only sessions whose header `cwd` matches the current directory are candidates.

`SessionManager.continueRecent(cwd)` uses this to resume: it calls `findMostRecentSession` and, if a match is found, loads that file; otherwise it creates a fresh session.

### The session header's cwd field

When `readSessionHeader()` reads the first 512 bytes of a file to check the header (without loading the whole file), it extracts the `cwd` field and compares it. A header whose `cwd` field is missing or empty (possible in old v1 sessions) is treated as a non-match for cwd-filtered queries.

### Cross-directory listing

`SessionManager.listAll()` walks every subdirectory under `~/.xzy/sessions/` and loads `SessionInfo` for every `.jsonl` file found. `SessionInfo` carries:

| Field | What it holds |
|---|---|
| `path` | Absolute path to the `.jsonl` file |
| `id` | Session id from the header |
| `cwd` | Working directory from the header |
| `name` | User-defined display name from the latest `session_info` entry |
| `parentSessionPath` | Header's `parentSession` value (fork lineage) |
| `created` | Timestamp from the header |
| `modified` | Latest message activity time, or header time as fallback |
| `messageCount` | Number of `message`-type entries |
| `firstMessage` | Text of the first user message |

Results are returned sorted by `modified` descending (most recent first). Up to 10 files are loaded concurrently.

## Step 9 — Session versioning and migration

The current session schema is **version 3**. The `SessionManager` automatically migrates older files on load and rewrites the file in the new format.

| Migration | What changes |
|---|---|
| v1 → v2 | Adds `id`/`parentId` to all entries (v1 had no tree structure). Converts `firstKeptEntryIndex` (an integer offset) to `firstKeptEntryId` (a string id) in compaction entries. |
| v2 → v3 | Renames any message with `role: "hookMessage"` to `role: "custom"`. |

```ts
export const CURRENT_SESSION_VERSION = 3;
```

If `migrateToCurrentVersion()` makes any changes, the file is immediately rewritten with `_rewriteFile()` before the session continues. This happens transparently — the user doesn't need to do anything.

## Putting it all together: an annotated ASCII tree

Here's a concrete session tree that uses all the entry types we've covered:

```
sess-001 (header, cwd=/home/user/proj)
│
aa000001 [user: "Set up a web server"]        ← parentId: null (root)
  └─ bb000002 [assistant: "Sure, here's..."]
       └─ cc000003 [compaction]                ← context trimmed here; older messages summarised
            └─ dd000004 [user: "Add auth"]
                 └─ ee000005 [assistant: "I'll add JWT..."]  ← label: "working-auth"
                      ├─ ff000006 [user: "Also add rate limiting"]   ← original continued path
                      │    └─ gg000007 [assistant: "Rate limiting done"]
                      └─ hh000008 [branch_summary: "Decided to add rate limiting instead"]
                           └─ ii000009 [user: "Actually, add caching instead"]  ← new branch
                                └─ jj000010 [assistant: "Caching done"]  ← current leaf
```

Key observations:

- The `compaction` entry at `cc000003` replaces the history of `aa000001` and `bb000002` with a summary. The LLM sees the summary first, then everything from `firstKeptEntryId` onward.
- The `label` entry (attached to `ee000005`) is a user-defined bookmark; it does not appear as a tree node — it is stored as a separate `label`-type entry in the file, and its resolved value is surfaced via `SessionTreeNode.label`.
- The `branch_summary` at `hh000008` is appended as a child of `ee000005` when the user branches. It tells the LLM what the abandoned `ff000006 → gg000007` path was about.
- The current `leafId` is `jj000010`. `getBranch("jj000010")` returns `[aa000001, bb000002, cc000003, dd000004, ee000005, hh000008, ii000009, jj000010]`.
- The file contains both paths (`ff000006`, `gg000007` and `hh000008`, `ii000009`, `jj000010`) — neither was deleted.

## Summary

Here's a quick reference for the main `SessionManager` operations:

| Operation | Method | What it does |
|---|---|---|
| Create new session | `SessionManager.create(cwd)` | New `.jsonl` file in `~/.xzy/sessions/<encoded-cwd>/` |
| Resume most recent | `SessionManager.continueRecent(cwd)` | Finds most recent `.jsonl` by mtime, falls back to new |
| Open specific file | `SessionManager.open(path)` | Loads an existing file by path |
| Fork to new cwd | `SessionManager.forkFrom(src, targetCwd)` | Copies all entries, new header with new cwd |
| In-memory (no file) | `SessionManager.inMemory()` | All operations work, nothing is written to disk |
| Append a message | `appendMessage(message)` | Adds child of current leaf, advances leaf |
| Move leaf pointer | `branch(entryId)` | Moves leaf to any existing entry; next append creates new child |
| Move to before root | `resetLeaf()` | Sets `leafId = null`; next append creates a new root |
| Branch with summary | `branchWithSummary(entryId, summary)` | Moves leaf + appends `branch_summary` entry |
| Clone path to new file | `createBranchedSession(leafId)` | New `.jsonl` with only root→leafId path |
| Read current context | `buildSessionContext()` | Returns ordered messages for the LLM, applying compaction |
| Walk leaf to root | `getBranch(fromId?)` | Array of entries from root to specified (or current) leaf |
| Whole tree | `getTree()` | `SessionTreeNode[]` mirroring the parentId structure |
| Label / bookmark | `appendLabelChange(targetId, label)` | Set or clear a label on any entry |
